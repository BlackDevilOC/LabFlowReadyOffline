# LabFlow — Offline Sync Strategy

> **Date:** 2026-06-14  
> **Status:** Proposed / Planning  
> **Author:** LabFlow Team

---

## 1. The Problem

The current LabFlow application was designed as a web-based app (FastAPI + Supabase) and later packaged as a desktop EXE via PyWebView + PyInstaller. It **requires an active internet connection** to function because all data operations depend on Supabase (PostgreSQL cloud database).

### Why the MR No. makes sync hard

- The **MR No.** is the primary key in the `patients` table and is used as a lookup key everywhere (test results, print previews, invoices, etc.).
- MR No. is auto-generated by Supabase (incremental integer). Two offline instances could generate the **same** MR No. for different patients, causing conflicts on sync.
- All existing pages, routes, and workflows reference patients by MR No. — retrofitting the entire app for offline support would require a massive rewrite.

### Two options considered

| Option | Description | Verdict |
|---|---|---|
| **Option 1** — Make the current app sync-based | Rewrite the entire app to work offline-first with a local DB (SQLite) and sync to Supabase. | ❌ **Too costly, risky, and time-consuming** for an app already in production. |
| **Option 2** — Build a separate offline version | Create a standalone offline mode that runs independently and syncs bulk data later via an admin panel. | ✅ **Clean separation, low risk, pragmatic.** |

**This document details Option 2.**

### Key Principles

1. **Zero changes to the existing online app** — the offline mode is a separate code path.
2. **Offline mode is self-contained** — uses local SQLite database (or JSON files) with no internet dependency.
3. **Sync is unidirectional (Offline → Online)** — offline records are pushed to Supabase; the offline mode never pulls live data.
4. **Offline IDs are clearly distinguishable** — prefixed with `OFF-` so they can never collide with online MR Nos.

## 3. Offline Mode — Data Model

### Local SQLite Schema

```sql
-- Patients registered while offline
CREATE TABLE offline_patients (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    offline_mr TEXT NOT NULL UNIQUE,       -- e.g. "OFF-1718340001"
    patient_name TEXT NOT NULL,
    salutation TEXT,
    relation TEXT,
    relation_name TEXT,
    mobile TEXT,
    gender TEXT,
    age INTEGER,
    cnic TEXT,
    shift TEXT,
    patient_token TEXT DEFAULT '0',
    user TEXT,
    user_id TEXT,
    created_at TEXT DEFAULT (datetime('now', 'localtime')),
    synced INTEGER DEFAULT 0,              -- 0 = pending, 1 = synced
    online_mr INTEGER,                     -- set after sync (Supabase MR No.)
    sync_error TEXT                         -- error message if sync failed
);

-- Tests selected for each patient (the tests they ordered)
CREATE TABLE offline_test_records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    offline_mr TEXT NOT NULL,              -- FK → offline_patients.offline_mr
    test_name TEXT NOT NULL,
    category TEXT,
    test_values TEXT,                      -- JSON string of parameter → value
    remarks TEXT,
    status TEXT DEFAULT 'Pending',
    created_at TEXT DEFAULT (datetime('now', 'localtime')),
    synced INTEGER DEFAULT 0,
    online_record_id INTEGER,              -- set after sync
    FOREIGN KEY (offline_mr) REFERENCES offline_patients(offline_mr)
);

-- Track sync batches
CREATE TABLE sync_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    batch_id TEXT NOT NULL,
    synced_at TEXT DEFAULT (datetime('now', 'localtime')),
    patients_count INTEGER,
    records_count INTEGER,
    status TEXT DEFAULT 'pending'          -- pending / success / partial / failed
);
```

### Alternative: JSON-based storage

If SQLite adds complexity, the same data can be stored as structured JSON files:

```json
{
  "offline_mr": "OFF-1718340001",
  "patient_name": "John Doe",
  "relation": "Self",
  "relation_name": "",
  "mobile": "0300-1234567",
  "gender": "Male",
  "age": 35,
  "shift": "MORNING",
  "tests": [
    { "test_name": "CBC", "category": "Hematology", "status": "Completed", "test_values": {"HB": 14.5, "WBC": 7800} },
    { "test_name": "Blood Sugar Fasting", "category": "Biochemistry", "status": "Pending" }
  ],
  "created_at": "2026-06-14 13:30:00",
  "synced": false
}
```

> **Recommendation:** Use SQLite for production — it provides querying, relational integrity, and avoids loading entire datasets into memory.

## 4. Offline ID Generation (OFF-XXXXX)

### Format

```
OFF-{timestamp_seconds}{random_2_digit}
```

### Examples

```
OFF-1718340001
OFF-1718340002
OFF-1718340053
```

### Uniqueness

- The timestamp portion (10 digits, Unix epoch seconds) ensures uniqueness across different PCs.
- The 2-digit random suffix handles multiple patients registered in the same second.
- The prefix `OFF-` is a string, so it **cannot collide** with Supabase integer MR Nos.

### Implementation

```python
import time
import random

def generate_offline_mr() -> str:
    ts = int(time.time())           # e.g. 1718340001
    suffix = random.randint(10, 99) # e.g. 53
    return f"OFF-{ts}{suffix}"      # e.g. "OFF-171834000153"
```

## 6. Sync Admin Panel

### Purpose

When the internet is available, an authorized user opens the **Sync Admin Panel** to push all offline records to Supabase.

### Sync Process

```
┌───────────────────────────────────────────────────────┐
│                 SYNC ADMIN PANEL                       │
│                                                        │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Pending Offline Records:   12                   │   │
│  │  Last Sync:                 Never                │   │
│  │                                                   │   │
│  │  [  🔄 Start Sync  ]                         │   │
│  │                                                   │   │
│  │  ● Sync will:                                    │   │
│  │    1. Insert patients into Supabase `patients`    │   │
│  │    2. Get online MR No. back                      │   │
│  │    3. Insert test records into `test_results_all` │   │
│  │    4. Mark records as synced locally              │   │
│  └─────────────────────────────────────────────────┘   │
│                                                        │
│  ┌─────────────────────────────────────────────────┐   │
│  │  SYNC LOG                                        │   │
│  │  ─────────────────────────────────────           │   │
│  │  Batch #3 — 2026-06-14 14:00   ✅ Success (5)    │   │
│  │  Batch #2 — 2026-06-13 10:30   ⚠️ Partial (2/3) │   │
│  │  Batch #1 — 2026-06-12 09:00   ❌ Failed        │   │
│  └─────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────┘
```

### Sync Algorithm (Pseudocode)

```python
def sync_offline_records():
    pending = local_db.query("SELECT * FROM offline_patients WHERE synced = 0")
    batch_id = generate_batch_id()
    
    for patient in pending:
        try:
            # Step 1: Insert patient into Supabase
            supabase_payload = {
                "patient_name": patient.patient_name,
                "relation": patient.relation,
                "relation_name": patient.relation_name,
                "mobile": patient.mobile,
                "gender": patient.gender,
                "age": patient.age,
                "shift": patient.shift,
                "user": patient.user or "Offline",
                "is_offline_sync": True,          # ← NEW COLUMN
                "original_offline_mr": patient.offline_mr,  # ← NEW COLUMN
            }
            result = supabase.table("patients").insert(supabase_payload).execute()
            online_mr = result.data[0]["mr_no"]
            
            # Step 2: Insert test records
            tests = local_db.query(
                "SELECT * FROM offline_test_records WHERE offline_mr = ? AND synced = 0",
                (patient.offline_mr,)
            )
            for test in tests:
                supabase.table("test_results_all").insert({
                    "mr_no": online_mr,
                    "patient_name": patient.patient_name,
                    "test_name": test.test_name,
                    "category": test.category,
                    "test_values": json.loads(test.test_values) if test.test_values else {},
                    "remarks": test.remarks or "",
                    "status": test.status,
                    "is_offline_sync": True,
                }).execute()
            
            # Step 3: Mark local records as synced
            local_db.execute(
                "UPDATE offline_patients SET synced = 1, online_mr = ? WHERE offline_mr = ?",
                (online_mr, patient.offline_mr)
            )
            local_db.execute(
                "UPDATE offline_test_records SET synced = 1 WHERE offline_mr = ?",
                (patient.offline_mr,)
            )
            
        except Exception as e:
            local_db.execute(
                "UPDATE offline_patients SET sync_error = ? WHERE offline_mr = ?",
                (str(e), patient.offline_mr)
            )
```

## 7. Supabase Schema Changes

Two new columns must be added to the existing `patients` and `test_results_all` tables:

### `patients` table — New Columns

| Column | Type | Default | Description |
|---|---|---|---|
| `is_offline_sync` | `BOOLEAN` | `FALSE` | Marks records that came from offline sync |
| `original_offline_mr` | `TEXT` | `NULL` | Stores the original OFF-XXXXX ID for traceability |

### `test_results_all` table — New Columns

| Column | Type | Default | Description |
|---|---|---|---|
| `is_offline_sync` | `BOOLEAN` | `FALSE` | Marks test records that came from offline sync |

### SQL for migration

```sql
ALTER TABLE patients 
ADD COLUMN is_offline_sync BOOLEAN DEFAULT FALSE;

ALTER TABLE patients 
ADD COLUMN original_offline_mr TEXT DEFAULT NULL;

ALTER TABLE test_results_all 
ADD COLUMN is_offline_sync BOOLEAN DEFAULT FALSE;

-- Index for filtering offline records
CREATE INDEX idx_patients_offline_sync ON patients(is_offline_sync);
CREATE INDEX idx_test_results_offline_sync ON test_results_all(is_offline_sync);
```

### How the online app uses these columns

- **Filtering:** The online app can exclude or visually differentiate offline-synced records.
- **Traceability:** `original_offline_mr` allows linking back to the original offline record if needed.
- **No duplicates:** The sync logic checks these columns to prevent double-syncing.

## 10. Key Design Decisions

### Why SQLite instead of JSON?

| Criteria | SQLite | JSON Files |
|---|---|---|
| Query performance | ✅ Fast with indexes | ❌ Must load all data |
| Relational integrity | ✅ Foreign keys | ❌ Manual management |
| Concurrent access | ✅ ACID compliant | ❌ Race conditions |
| Sync partial updates | ✅ Easy (UPDATE ... WHERE) | ❌ Must rewrite files |
| Setup complexity | ⚠️ Need dependency | ✅ Built-in |

### Why a separate code path instead of modifying existing routes?

- **Zero risk** to the production online app.
- **Simpler testing** — offline mode can be tested independently.
- **Cleaner code** — no conditional branches (`if offline: ... else: ...`) cluttering existing logic.
- **Easy rollback** — if offline mode has issues, users can still use the online app.

### Why `OFF-` prefix instead of UUIDs?

- **Human-readable** — lab staff can read and communicate IDs easily.
- **Short** — fits on printed reports without truncation.
- **Sortable** — timestamp-based ordering.
- **Unmistakable** — `OFF-` at a glance tells staff this was an offline registration.

## 11. Risks & Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Duplicate patient sync | Duplicate records in Supabase | Check `original_offline_mr` before insert; use `ON CONFLICT` handling |
| Network failure during sync | Partial sync (patients synced but not tests) | Record sync in `sync_log`; support resume/retry per patient |
| Two PCs sync same patient in offline mode | Two separate online MR Nos for same person | Staff is expected to check existing patients; optional: add CNIC lookup before sync |
| SQLite file corruption | Loss of all offline data | Regular local backups; export-to-JSON fallback |
| Large offline dataset | Slow sync | Batch processing (sync 10 patients at a time); show progress bar |
